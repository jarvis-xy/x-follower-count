# 实现说明

2026-10-09 · v1.0.0

参照 @yiren_ai 的推文（2026-10-09）做的 Chrome 插件：在 X 页面的用户名旁显示粉丝数。推文里的思路是「X 页面自己发出的请求里已经包含粉丝数字段，直接拿过来用」，本插件按这个思路实现。

## 数据从哪来

`extension/src/inject.js` 在页面的主环境（`"world": "MAIN"`）里、X 脚本运行之前加载，包装 `XMLHttpRequest` 和 `fetch`：

- 只看 URL 含 `/i/api/`、`/graphql/` 或 `api.x.com` 的响应，状态码 2xx、内容是 JSON 的才解析
- 在 X 自己的回调执行完之后（`setTimeout 0`）再解析，不拖慢 X 渲染
- 遍历整个 JSON，找出用户对象，提取 `{用户名, 粉丝数, 关注数}`，通过 `CustomEvent`（内容是 JSON 字符串）发给插件的隔离环境脚本
- 同一用户的数字没变就不重复发；隔离环境脚本启动时发 `xfc:ready`，主环境脚本就把已收集到的全部重发一次，以应对两个脚本的加载先后不确定

**X 的用户对象有过三种结构，三种都支持：**

| 结构 | 用户名 | 粉丝数 | 关注数 |
| --- | --- | --- | --- |
| 2026 年 GraphQL（当前线上） | `core.screen_name` | `relationship_counts.followers` | `relationship_counts.following` |
| 早期 GraphQL | `core.screen_name` 或 `legacy.screen_name` | `legacy.followers_count` | `legacy.friends_count` |
| REST v1.1 | `screen_name` | `followers_count` | `friends_count` |

> 2026-10-09 在真实 x.com 上抓 `HomeTimeline` 核对过：53 个用户对象**全部没有 `legacy` 字段**，粉丝数只在 `relationship_counts.followers` 里。网上大多数教程和脚本还在读 `legacy.followers_count`，照着做在今天的 X 上会一个数都拿不到。X 再改版时，先查这里。

## 标签插在哪

`extension/src/content.js`（插件隔离环境）负责缓存、设置和渲染：

- **找容器**：`[data-testid="User-Name"]`（推文头部，含引用推文）和 `[data-testid="UserCell"]`（关注者、正在关注、推荐关注、点赞列表、搜索用户）。悬停卡片里不显示（X 自带粉丝数）
- **找用户名**：遍历容器里的文本节点，取第一个恰好是 `@xxx` 的。不用链接的 `textContent`，因为翻译类插件（实测 Tabbit 自带翻译）会往 @用户名 的 span 里塞自己的节点。简介里的 @提及 总在真实用户名之后，不会误取。引用推文的头部没有链接，用文本节点照样能找到
- **找插入位置**：用户名之前第一个带 `dir` 属性的文本块就是显示名，它的父元素是「显示名 + 认证标」那一小行（横向 flex），标签追加到这一行末尾，所以总在 ✓ 后面、同一行

> 坑：一开始的方案是从显示名的链接往上找第一个横向 flex 容器，再插在它后面。推文里没问题，但在真实的 UserCell 里，第一个横向容器是「名字信息列 + 回关按钮」那一行，标签会跑到回关按钮旁边。改成插进显示名所在的那一小行后，推文和列表里位置都对。X 的基础类名也变过（`css-175oi2r` → `css-g5y9jx`），所以代码只看计算后的样式，不认类名。

- **更新**：`MutationObserver` 监听 `document` 的节点增减，80ms 合并一次重扫。已有标签时只比对用户名和数字，变了才改，所以虚拟列表回收节点、React 复用节点换了作者都能跟上
- **主题**：根据 `body` 背景色亮度，在 `<html>` 上标 `data-xfc-theme`，深色主题用更亮的配色

## 未回关标记（v1.1.0）

在用户列表（UserCell）里，给「你关注了、但没有关注你」的人在 @用户名后标一个红色「未回关」，和 X 自带的「关注了你」放在同一行同一位置。

**判断依据只看列表行本身，不用接口数据：**

- 你关注了对方：这一行关注按钮的 `data-testid` 以 `-unfollow` 结尾（按钮显示「正在关注」）
- 对方关注了你：这一行有 X 自带的 `[data-testid="userFollowIndicator"]`（「关注了你」）
- 两条同时满足「你关注了、但没有那个标签」才标

不用接口里的 `relationship_perspectives.following / followed_by`，原因有两个：一是关系数据只对当前登录账号有效，不该进缓存；二是你在页面上点「取消关注」后，X 不会重新请求这个用户，接口数据会过时，而按钮的 `data-testid` 会当场变。为了捕捉这种「属性原地变化」，`MutationObserver` 额外监听了 `data-testid` 属性（`attributeFilter`），只加这一个属性，开销可以忽略。

位置：从 @用户名 的文本节点往上找第一个横向 flex 容器，也就是 X 放「关注了你」的那一行，把标签追加到行尾。

> 2026-10-09 在真实的「正在关注」列表上核对：22 行里，X 的「关注了你」标签和接口 `followed_by` 完全一致（0 处不符）。列表顶部 22 行中应标 7 行，实际标出 7 行，无漏标、无误标、无重复。用户截图里的几个账号也都对上了。

## 缓存与设置

- 设置存在 `chrome.storage.sync`：`enabled / showInTweets / showInLists / lang / tierColors`，弹窗改动后实时生效
- 粉丝数存在 `chrome.storage.local` 的 `xfcCache`，格式是 `{用户名小写: [粉丝, 关注, 时间戳, 原始用户名]}`。3 秒防抖写入；写入前先读出再合并，避免多个 X 标签页互相覆盖；超过 1 万条时淘汰最旧的
- 弹窗里点「清空记录」：删掉存储，所有标签页清空内存，并发 `xfc:reset` 让主环境脚本也忘掉已发送记录。这样标签会消失，等 X 返回新数据后再出现，计数不会马上又涨回来

## 没做的 / 待决

- **商店上架**：2026-10-09 已提交 Chrome 应用商店审核，商店名为 X Follower Count，审核通过后自动发布。各字段填法和状态见 [store/listing.md](../store/listing.md)
- **没做 Firefox 版**。Firefox 的 MV3 支持 `world: "MAIN"` 的时间晚，事件传数据的方式也不同，要单独适配
- **没做粉丝列表排序 / 导出**。数据已经在缓存里，加一个「按粉丝数排序当前列表」或导出 CSV 的功能不难，按需求再定
- **X Pro（TweetDeck）、私信列表、通知里的名字没覆盖**，这些地方的页面结构不同
- 依赖 X 的页面结构（`data-testid`、文本元素带 `dir`）和接口字段。X 改版后先跑一遍 `npm run test:e2e`；如果模拟页面上通过而真实页面上不显示，就是 X 改了，先查上面两处「坑」
